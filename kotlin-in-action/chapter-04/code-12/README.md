# Introduction: `data class`
A `data class` is a class whose main purpose is to hold data.  
By simply adding the `data` modifier, Kotlin asks the compiler to generate common meethods automatically.

## Regular `class` vs. `data class`
For a regular `class`, methods such as `equals`, `hashCode`, and `toString` are inherited from `Any` class unless they are explicitly overridden.  
This means two separate instances are not equal by default, even if they contain the same property values.
- That is, the `equals` method returns `false`, and the `hashCode` method makes distinct hash codes for two separate instances whose memory addresses are different.

For a `data class`, Kotlin automatically generates the following methods:
- `equals()` for comparing instances **by value**
- `hashCode()` for using instances in hash-based containers such as `HashMap` and `HashSet`
- `toString()` for producing a readable string representation
- `copy()` for creating a new instance with the same property values (or some properties changed)

### NOTE!!
**Importantly, the generated `equals` and `hashCode` use only the properties declared in the primary constructor.**  
- Properties declared inside the class body are not included in equality checks or hash code calculation.

Data classes are usually best used with **read-only properties (`val`)** so that instances behave like immutable value objects.

## Declaring a `data class`
This is an example of a `data class` from 'Kotlin in Action 2/e'.  
You can see that the behavior of the automatically generated methods (`equals`, `toString`, and `hashCode`) exhibit their behavior different from the case of a regular `class`.  
- `equals`: If **properties declared in the primary constructor** are identical between two separate instances, the `equals` method treats them as the same.
- `toString`: The string representation shows all the properties in declaration order.
- `hashCode`: If two instances are equal according to `equals`, `hashCode` makes an identical hash code for them.

```kotlin
data class Customer(val name: String, val postalCode: Int){
    // The property below is not declared in the primary constructor.
    val myVar = 0   // `toString` does not show this. `equals` and `hashCode` does not reflect this property.
}

fun main() {
    val c1 = Customer("Sam", 11521)
    val c2 = Customer("Mart", 15500)
    val c3 = Customer("Sam", 11521)
    println(c1)
    // Customer(name=Sam, postalCode=11521)
    println(c1 == c2)
    // false
    println(c1 == c3)
    // true
    println(c1.hashCode())
    // 2580770
    println(c3.hashCode())
    // 2580770
}
```

## The `copy` method of a `data class`
Kotlin compiler generates one more method: `copy`.
- It would be best to declare and use `data class`es as immutable objects, rather than mutable ones.
- Instead, when you want to modify properties of immutable objects, it can be a good way to **create a copy with some property values modified, utilizing the `copy` method.**
  - It is safer than changing the original object in place.

```kotlin
data class Customer(val name: String, val postalCode: Int){
    val myVar = 0

    // If you manually declare the `copy` method, it would look like the method below.
    /*
    fun copy(name: String = this.name, postalCode: Int = this.postalCode) = Customer(name, postalCode)
    */
}

fun main() {
    val bob = Customer("Bob", 973293)
    println(bob)
    // Customer(name=Bob, postalCode=973293)
    println(bob.copy(postalCode = 382555))  // making a copy with a property (`postalCode`) modified
    // Customer(name=Bob, postalCode=382555)
}
```

### Recommendation
Well, the primary constructor of a `data class` can contain one or more `var` properties.  
Nevertheless, there is a recommendation:
>> **`data class` is recommended to only have `val` properties (i.e., read-only properties) as much as possible.**
- If you observe this recommendation, the `data class` would be *immutable*.
- **When you want to use some instances as keys in hash-based collections, it is especially worth adhering, even though the compiler does not enforce this.**
- Futhermore, it is helpful when you handle multithreaded code.
  - Immutable `data class` are easier to reason about, especially in multithreaded code.
  - It is because their state cannot change after creation.

For instance, the following source code is not impossible in terms of its syntax **but not recommended**:
```kotlin
data class Customer(
    var name: String,
    var postalCode: Int
)

fun main() {
    // A hash code of the instance is calculated, a corresponding bucket is created, and the instance would be stored in the bucket.
    val anInstance = Customer("Alice", 342562)
    val processed = hashSetOf(anInstance)

    println(anInstance in processed)
    // true

    anInstance.postalCode = 999999
    println(anInstance in processed)
    // false
}
```
- In above source code, the `hashCode` method use the two properties of `Customer("Alice", 342562)`: `var name` & `var postalCode`.
- If you modify `var name` or `var postalCode` of `anInstance`, the properties of the stored instance would be also modified accordingly.
  - After that, you may no longer be able to find `anInstance` in the hash set `processed`.
  - It occures because of hash code mismatch. `anInstance` is actually in `processed` but the hash code of `anInstance` points at other hash bucket.

## Kotlin `data class`es and Java `record`s
In Java 14, records were introduced and are similar to `data class` in Kotlin.
- They hold immutables values.
- Records also automatically make some methods: `toString`, `hashCode`, and `equals`.  
- Records don't have other convenient functions such as `copy`.

However, there are more structural restrictions in 'Java records':
- All properties are supposed to be `private` and `final`.
- A record cannot inherit from other class and become a superclass of other classes.
- It is not permitted to declare additional properties (instance fields) in the body. All properties must be declared in the header. (e.g., `record Name(String name, int age)`)

### When it comes to interoperability
If you want to use Kotlin `data class` from Java, you can simply annotate a `data class` with `@JvmRecord`.  
Then, you can use the `data class` as Java `record` from Java.  
In other words, the `data class` looks like `Java record` to JVM bytecode.

**In such case, the `data class` is required to comply with the structural restrictions which apply to Java records.**
- Otherwise, Kotlin compiler error may arise.

There is an example:
```kotlin
// (1) Specifying a superclass is prohibited.
// But `data class` with `@JvmRecord` can also implement interfaces.
@JvmRecord
data class Person(
    // (2) var is not allowed.
    val name: String,
    val age: Int
){
    /*
    (3) It is not permitted to declare "additional properties with the backing field" in the class body.
    */
}
```
From the perspective of Java, the above `data class` can be seen like the code below:
```java
public record Person(String name, int age) {}
```

## Whether or not overriding autogenerated methods is possible
### Possible things: `equals`, `hashCode`, and `toString`
You can explicitly override these three methods.  
If overriding them, the overridden version would be used.  

Remember that **if you override `equals`, it is strongly recommended to override `hashCode` as well.**

### Impossible things: `copy`, `componentN` (`component1`, `component2`, etc.)
In first, you cannot manually override `copy`.  
If you really wanna do that, there are a few alternatives.
- (1) Just using a regular `class`
- (2) Newly declaring a method with a separate name (e.g., `copyWithValidatedPostalCode`).

In second, you are not able to override `componentN` (e.g., `component1()`, `component2()`, etc.).  
This method is autogenerated for "destructuring declaration".  
That is, `componentN` enables the following:
```kotlin
data class Customer(
    val name: String,
    val postalCode: Int
)

fun main() {
    val customer = Customer("Alice", 342562)

    val (name, postalCode) = customer   // `component1()` and `component2()` play a role here!
    println(name)
    println(postalCode)
}
```

However, in the case of `data class`, explicitly overriding is prohibited.  
That is, you cannot do the following:
```kotlin
data class Customer(
    val name: String,
    val postalCode: Int
) {
    operator fun component1(): String = name.uppercase()
    // Error
}
```

On a side note, you can directly implement `componentN()` methods in the case of regular `class`es, using the `operator` keyword.
- `operator fun component1() = ...`
